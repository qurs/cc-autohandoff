# Устройство и ограничения

Начальная версия перенесена из установленного пользовательского плагина
`codex-handoff` 0.1.1. Общая машина состояний сохранена:
`monitoring → generating → ready | failed`. Retry явно переводит `failed` в `generating`.
Блокировка файла предотвращает одновременный запуск нескольких writers одной сессии.

## Две среды

Один Python CLI обслуживает обе среды; `--platform codex|claude` выбирает формат transcript,
модель и CLI writer. По умолчанию используется Codex. При `status` и `retry` среда
восстанавливается из `session.json`.

Codex читает последнее `last_token_usage` из `event_msg/token_count` либо
`token_usage_record.payload.usage`. Накопленные `total_token_usage` не используются.
Claude Code читает usage последнего основного сообщения `assistant`: input, output,
cache creation и cache read. Они складываются внутри одного ответа, не между ответами.
Неполная строка JSONL перечитывается следующим hook. Без usage порог не считается
подтверждённым; пользователь видит предупреждение.

Hooks: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `PreCompact`.
После порога `PreToolUse` отклоняет новые инструменты, `UserPromptSubmit` блокирует новую
работу, `PostToolUse` передаёт инструкции модели. `Stop` может один раз попросить модель
выдать ссылки, затем завершает ход. В desktop-режиме дополнительно разрешены ограниченные
операции доставки, описанные ниже. Уже запущенные инструменты и фоновые процессы
не прерываются. Порог проверяется на границах hooks; точная остановка на токене 150 000
внутри генерации не гарантируется.

В Codex `PreCompact` возвращает `continue: false`. Claude Code требует
`decision: "block"` и игнорирует `continue`/`systemMessage` этого события.
Для Claude Code нужна версия 2.1.295+ с поддержкой блокировки `PreCompact`, exec-form hooks
(`command` + `args`) и `onFailure: block`. На старых версиях контракт не гарантируется.

## Доставка в Codex desktop

`continuation.codex = codex-desktop` разрешает основной модели после `ready` вызвать
`mcp__codex_app__list_projects` с `{}`, затем `mcp__codex_app__create_thread` и
`mcp__codex_app__navigate_to_codex_page`. Сам процесс hook не имеет доступа к этим инструментам.
При `manual` и у старого состояния без режима продолжения автосоздания нет.
Выбор проекта требует единственного совпадения абсолютного пути с рабочей папкой,
`projectKind = local` и `hostId = local`. Используется локальная среда, без worktree.
Prompt равен сохранённому `START-NEXT-SESSION.txt`; модель и reasoning нового чата
не переопределяются. Writer по-прежнему не имеет инструментов и только готовит handoff.

Отдельное состояние `continuation` проходит этапы
`pending → discovering → project_ready → creating → created → opening → opened`.
До разрешения вызова `PreToolUse` под блокировкой сохраняет его имя и `tool_use_id`.
`PostToolUse` принимает только соответствующий ответ. Список проектов читается из
MCP `structuredContent` либо единственного JSON-текстового блока `content`.
Ответы сохраняются в `desktop-discovering.json`, `desktop-creating.json`,
`desktop-opening.json` внутри каталога handoff; эти файлы не попадают в Git.
Остальные инструменты после порога заблокированы. Это ограничение действует в пределах
путей tools, поддерживаемых hooks; hooks не являются полной границей изоляции.

Повтор `PreToolUse` не разрешает уже зарезервированный вызов. Если ответ потерян,
`Stop` или `SessionStart` фиксирует `failed`, `uncertain` либо `open_failed`.
Автоматического повтора нет. Ответ с `clientThreadId` переводит доставку в `queued`:
выдаётся карточка очереди, идентификатор не передаётся инструменту открытия.
Подтверждённый `threadId` сохраняется и выводится карточкой даже при ошибке открытия.
Отключение режима запрещает новые вызовы, сохраняя уже полученные подтверждения.

`Stop` может запросить каждый из трёх этапов доставки только один раз и затем один раз
попросить финальные ссылки и карточку. Маркер `CODEX_HANDOFF_DELIVER:<session-key>`
пропускает такой служебный prompt через `UserPromptSubmit`, но не снимает блокировку tools.
Это предотвращает бесконечную цепочку `Stop`, если инструменты недоступны или модель
не выполнила запрос. Артефакты и диагностика остаются доступны пользователю.

`retry-continuation --session-dir ...` сбрасывает только неудавшуюся доставку, не writer.
Для `uncertain` требуется `--confirm-no-chat` после ручной проверки списка чатов;
плагин не может доказать отсутствие чата при потере ответа. Для `open_failed` повтор
разрешает только открыть сохранённый чат. При `created`, `opened`, `queued` или ещё
зарезервированном вызове повтор отклоняется. После retry нужен служебный prompt
в старом чате; команда не вызывает приложение самостоятельно.

## Доставка в Claude desktop

`continuation.claude = claude-desktop` действует, только если хост запущен из приложения
Claude (`CLAUDE_CODE_ENTRYPOINT = claude-desktop`); в CLI и IDE режим понижается до `manual`
в момент срабатывания порога и сохраняется в состоянии. После `ready` основной модели разрешены
два вызова: `ToolSearch` ровно с запросом `select:mcp__ccd_session__start_session`
(инструмент приложения отложенный, загрузка схемы не имеет побочных эффектов) и один
`mcp__ccd_session__start_session` с аргументами, которые строит плагин: `initiation: user_asked`,
`context: fresh`, `use_worktree: false`, `prompt` равен `START-NEXT-SESSION.txt`, `background`
повторяет запрет читать прежнюю историю. Любое отличие аргументов отклоняется.

Этапы: `pending → creating → created`. `PreToolUse` под блокировкой резервирует вызов
по `tool_use_id`; повторный вызов отклоняется. `PostToolUse` сохраняет ответ в
`desktop-creating.json` и ищет в его строках идентификаторы `local_…`, кроме собственной
сессии. Ровно один идентификатор без `isError` даёт `created`; иначе — `uncertain`.
Потерянный ответ (`Stop`/`SessionStart` во время `creating`) тоже даёт `uncertain`.
`Stop` один раз просит выполнить создание и один раз — финальный ответ. Доставка считается
завершённой, когда ответ содержит ссылки на оба файла и ссылку `#local_…` новой сессии.
`retry-continuation` работает так же, как в Codex: для `uncertain` нужен
`--confirm-no-chat` после проверки списка сессий, при `created` повтор запрещён.

## Writer и артефакты

Writer запускается через локальный авторизованный CLI, отдельный API-ключ плагин не требует.
В Claude Code CLI ищется в `CC_AUTOHANDOFF_CLAUDE`, затем в PATH, затем в
`CLAUDE_CODE_EXECPATH` (CLI, встроенный в приложение). Дочерний `claude --print` не наследует
вход приложения, поэтому `SessionStart` вызывает `claude auth status` и при `loggedIn != true`
показывает пользователю предупреждение с командой `claude auth login`. Ошибка 401/403 из
JSON-ответа writer попадает в категорию `authentication` и сопровождается той же подсказкой.
Codex использует ephemeral read-only `codex exec`; Claude Code — print mode без сохранения
сессии, инструментов и MCP. Hooks writer отключены; дополнительная переменная окружения
защищает от рекурсии. Модели фиксированы, fallback запрещён.

Текст handoff, заголовки и служебные пояснения в `HANDOFF.md` составляются на английском.
Русские цитаты, названия, UI-тексты, пути, команды и ошибки сохраняются в оригинале,
если важна точная формулировка. Языковые требования пользователя к дальнейшей работе
передаются как ограничения и не меняют язык handoff. Стартовый prompt также составляется
на английском; уведомления пользователю остаются на русском.

Плагин читает transcript, который ведёт сам хост, и формирует вход writer только в памяти.
Пользовательские и текстовые ответы агента, вызовы инструментов и их результаты передаются
через stdin, без сохранения снимка переписки. Длинные технические выводы обрезаются с явным учётом пропусков.
Изображения представлены отметками; system/developer и скрытые рассуждения не экспортируются.
Если пользовательский текст превышает бюджет, генерация завершается ошибкой вместо
молчаливой потери текста. Ответ writer проверяется по схеме до публикации handoff.

В `.cc-autohandoff/<session-key>/` сохраняются `session.json`, `writer-request.json`,
диагностика writer, `HANDOFF.md`, `START-NEXT-SESSION.txt` и квитанции доставки desktop.
`SOURCE.jsonl` и `source-manifest.json` не создаются; прежние копии в каталоге текущей
генерации удаляются перед запуском writer. Произвольные stdout/stderr writer не записываются:
они могут повторять исходную переписку. `writer-errors.log` содержит только модель,
код выхода, признак тайм-аута, размеры потоков и предполагаемые категории ошибок из
фиксированного списка. Промежуточный `writer-result.json` удаляется после обработки,
включая ошибки проверки. Transcript самого Codex/Claude Code плагин не удаляет и не копирует.
Состояние сохраняет путь к нему для мониторинга и явного retry, но не текст сообщений.

Последнее сообщение hook, ещё не записанное хостом, тоже передаётся только через память.
В состоянии остаются его роль и SHA-256. Если writer завершился ошибкой, а сообщение
отсутствует в исходном срезе transcript, обычный retry явно откажет вместо потери уточнения.
В этом случае `retry --session-dir ... --last-message-stdin` принимает точный текст через
stdin и сверяет SHA-256; файл с сообщением создавать не нужно.

В `HANDOFF.md` нет раздела со ссылками на transcript, снимок и исходный чат.
Writer не должен добавлять такие ссылки и ссылки на строки исходной переписки.
В сводке и стартовом prompt явно запрещены чтение и поиск прежнего чата через файловую
систему и инструменты чатов: единственный источник истории — `HANDOFF.md`.
Если сведений не хватает, модель должна спросить пользователя. Рабочие файлы проекта
разрешено проверять по задаче. Это инструкция модели, а не файловая изоляция хоста.

Все артефакты сессии исключены из Git. Ошибка оставляет сессию заблокированной;
уведомление содержит точную команду `retry`. Сообщение пользователя, равное
`CC_AUTOHANDOFF_RETRY`, в состоянии `failed` повторно запускает writer прямо из чата
(`UserPromptSubmit`); в остальных состояниях оно блокируется как обычный prompt. Путь CLI можно задать через
`CODEX_HANDOFF_CODEX` или `CC_AUTOHANDOFF_CLAUDE`.

## Начальный размер контекста

Новый чат получает не только стартовый prompt и прочитанный handoff, но и инструкции
среды, применимые `AGENTS.md`, каталог навыков и определения доступных инструментов.
[Документация Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
описывает загрузку инструкций проекта;
[документация tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)
подтверждает, что определения инструментов занимают контекст.
Поэтому перенос в новый чат не означает нулевой стартовый расход токенов.
Значение около 30 тысяч само по себе не доказывает загрузку старой истории:
для точной атрибуции нужно сравнить usage первого запроса нового чата в том же проекте
с теми же плагинами до и после чтения handoff. Плагин не измеряет размер системных инструкций
отдельно. Ранее чтение сохранённого `SOURCE.jsonl` могло дополнительно загружать старую переписку.

## Автономный пакет Windows x64

`scripts/build_plugin.py` собирает Python runtime через PyInstaller в onedir-формате.
`bin/cc-autohandoff.exe` определяет корень пакета по своему расположению, поэтому
находит настройки, схему и инструкции после копирования в cache приложения.
Перед внешним writer восстанавливается системный поиск DLL; bundled библиотеки
не должны попадать в отдельно установленный CLI. stdin/stdout hooks используют UTF-8.

Исходные hooks остаются Python-командами. Сборщик создаёт отдельные JSON-конфигурации:
Codex использует `commandWindows` с Windows PowerShell launcher `scripts/hook.ps1`,
который передаёт stdin/stdout и код возврата executable. Claude Code запускает `.exe`
напрямую через `command` и `args`, без shell. `onFailure: block` закрывает путь
продолжения работы при сбое launcher на `PreToolUse`, `UserPromptSubmit`, `PreCompact`.

В `master` находятся каталоги marketplace Codex и Claude Code. Оба используют источник
`source: url`, URL `https://github.com/qurs/cc-autohandoff.git` и `ref: windows-x64`.
Эта отдельная ветка содержит готовый пакет с runtime; менеджер плагинов получает его
через Git при установке `cc-autohandoff@cc-autohandoff`. В готовом пакете оба каталога
marketplace ссылаются на его корень. Пользователю не нужны Python, архивы или сборка.

Workflow `package.yml` запускает unit-тесты, сборку и проверку исполняемого пакета на
Windows, сохраняет artifact вместе со скрытыми каталогами, затем на Ubuntu повторно
проверяет его checksums и публикует только содержимое пакета в `windows-x64`.
Публикация разрешена после push в `master` или ручного запуска из `master`; pull request
не получает права записи. Ветка обновляется без force-push. Последовательный запуск
workflow предотвращает конфликт двух публикаций. Сбой сборки или проверки оставляет
предыдущий опубликованный пакет доступным. Изменения пакета требуют новой версии
в обоих manifests, чтобы менеджеры плагинов обновляли установленную копию.

Сборка копирует только разрешённые файлы, runtime и лицензии; SHA-256 manifest включает
все файлы кроме самого manifest. Проверка целостности не заменяет подпись издателя.
Сгенерированный `.gitattributes` отключает преобразование строк Git для всех файлов
пакета: после установки checksums совпадают и при включённом `core.autocrlf`.
`scripts/check_package.py` запускает пакет из каталога с пробелами и кириллицей,
задавая `PATH` с одним пустым каталогом и вызывая PowerShell по абсолютному системному
пути. Его сценарии используют синтетические transcript и заведомо отсутствующий writer
CLI, не выполняют запросы к моделям,
не устанавливают плагины и не изменяют пользовательскую конфигурацию.

## Проверка перед выпуском

Unit-тесты используют синтетические transcript и подменённый writer, без сетевых запросов.
Они не подтверждают доступ к моделям, реальную загрузку plugins и доставку hooks в UI.
Живой read-only `list_projects` подтвердил формат списка проектов. Создание и открытие
чата в полном цикле плагина пока проверены только с подменёнными ответами.
Перед выпуском нужно проверить обе среды с живыми CLI: достижение порога, выдачу ссылок,
ручной и автоматический compact, отказ модели, retry, пути с пробелами и Windows/POSIX.
Удалённая установка через Codex CLI и Claude Code CLI проверена в отдельных профилях.
Живая генерация Luna на синтетической переписке прошла; подробные результаты и оставшиеся
ограничения перечислены в [отчёте Windows x64](validation-windows-x64.md).
